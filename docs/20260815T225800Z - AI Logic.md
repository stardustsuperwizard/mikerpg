# AI Logic

## Prompt 1
Yeah let’s talk about ai logic for a moment. That’s something that should probably also be separate right? 

## Repsonse 1
Yes. **The AI decision logic should be separate from Bones.**

Bones should probably define the *hook* that lets AI control an actor, but it should not dictate *how AI thinks*. That keeps the framework from becoming opinionated about behavior trees vs utility AI vs GOAP vs state machines vs scripted encounter logic.

A clean split would look like this:

```text
bones/
└── core/
    └── controllers/
        ├── actor_controller.gd
        ├── player_controller.gd
        └── ai_controller.gd   # interface / adapter only
```

Then the actual AI implementation lives elsewhere:

```text
addons/
└── mikerpg_ai/
    ├── behavior_tree/
    ├── utility/
    ├── perception/
    ├── blackboard/
    └── controllers/
        └── behavior_ai_controller.gd
```

The important distinction is:

```text
Bones:
"What action do you want this actor to attempt?"

AI addon:
"How do I decide what action I want?"
```

So an AI controller might ultimately do something conceptually like:

```gdscript
func choose_action(actor):
    return brain.decide(actor, world_state)
```

and then hand that action back to the exact same system used by players and GMs:

```text
AI Brain
   ↓
AI Controller
   ↓
AttackAction(goblin, player)
   ↓
Authority
   ↓
Rules
   ↓
Combat
```

That is a really useful boundary because **AI does not execute combat**. It doesn't move actors directly, subtract hit points, or bypass the rules engine. It merely selects intent.

That gives you some interesting interchangeability.

Someone could install a behavior-tree addon:

```text
Goblin
  ↓
BehaviorTreeController
```

while another game uses utility AI:

```text
Goblin
  ↓
UtilityAIController
```

and a boss could use a completely scripted controller:

```text
Dragon
  ↓
EncounterScriptController
```

All three ultimately produce the same Bones actions.

I would even question whether Bones needs a concrete `AIController` at all. It may only need a generic controller abstraction:

```gdscript
class_name ActorController

func get_next_action(actor) -> Action:
    return null
```

Then implementations become:

```text
PlayerController
GMController
BehaviorTreeController
UtilityController
ScriptController
RemoteController
```

Now **AI isn't even special to Bones**.

That is arguably cleaner.

The framework's abstraction becomes:

> An Actor can be driven by a Controller. A Controller produces intents/actions.

Everything else is somebody else's problem.

That gives you a very attractive ecosystem model:

```text
                    BONES
                      │
              Controller API
                      │
        ┌─────────────┼──────────────┐
        │             │              │
      Player          GM             AI
    Controller       Addon          Addon
                                    │
                         ┌──────────┼──────────┐
                         │          │          │
                    Behavior      Utility     GOAP
                      Tree
```

And there is another reason I like this separation: **AI logic changes dramatically depending on the type of game.**

Your real-time RPG may want:

```text
perception
threat tables
cooldowns
movement steering
utility scores
```

Your turn-based tactical game may want:

```text
evaluate board
score possible moves
choose best action
end turn
```

Your NPC town simulation might want:

```text
schedule
needs
jobs
relationships
goals
```

Trying to make one "MikeRPG AI system" cover all of those would eventually make Bones very opinionated.

Instead Bones can provide the vocabulary they all operate against:

```text
Actor
Action
World
Target
Position
Attribute
Rule
Controller
```

An AI addon reads those things and produces an `Action`.

That's also where your earlier noun/action idea starts paying dividends. The AI doesn't need intimate knowledge of every game system. It can inspect **nouns/world state** and choose **verbs/actions**.

So I would draw the line like this:

```text
BONES
  Actor
  Controller contract
  Action contract
  Action execution
  Authority
  Rules
  World access

OPTIONAL AI ADDON
  perception
  memory
  blackboard
  behavior trees
  utility scoring
  GOAP
  threat systems
  tactical evaluation
```

The one thing I *might* keep in Bones is a very dumb reference controller, something like `SimpleAIController`, purely so the framework can demonstrate that the contract works:

```text
if enemy nearby:
    attack
else:
    idle
```

But I'd treat that exactly like the default ENet adapter: **a reference implementation, not the architecture.**

That would leave Bones pleasantly small and extensible.
