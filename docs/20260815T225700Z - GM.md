# Runtime

## Prompt 1
How does GM integration work? Could the be a separate add on that provides a new controller too bones?

## Response 1
Yes. **GM support is a very good candidate for a separate addon**, and the cleanest integration point is indeed the controller layer.

In Bones, an `Actor` should not fundamentally care whether its decisions come from a player, AI, GM, scripted cutscene, replay system, or something else. The controller answers the question: **“Who or what is choosing actions for this actor?”**

So Bones could define the contract:

```text
bones/
├── core/
│   ├── actors/
│   ├── actions/
│   ├── authority/
│   └── controllers/
│       ├── controller.gd
│       ├── player_controller.gd
│       └── ai_controller.gd
```

Then a completely separate addon could provide:

```text
addons/
└── mikerpg_gm/
    ├── controllers/
    │   └── gm_controller.gd
    ├── commands/
    │   ├── spawn_actor.gd
    │   ├── possess_actor.gd
    │   ├── teleport_actor.gd
    │   └── grant_item.gd
    ├── ui/
    │   ├── gm_panel.tscn
    │   └── actor_inspector.tscn
    └── plugin.cfg
```

The important thing is that `GMController` doesn't need special privileges simply because its class name contains "GM."

It might extend the normal controller:

```gdscript
class_name GMController
extends ActorController

func request_action(actor, action):
    return action_system.request(actor, action)
```

What makes it powerful is **authority**.

That gives you a nice separation:

```text
Controller
    "I want Actor X to perform Action Y."
            │
            ▼
Authority
    "Is this controller allowed to request that?"
            │
            ▼
Rules
    "Is this action mechanically legal?"
            │
            ▼
Action executes
```

And that is particularly important for GM mode.

A normal player might request:

```text
PlayerController
    ↓
Move(my_character, destination)
```

Authority checks:

```text
Does PlayerController own my_character?
YES
```

A GM might request:

```text
GMController
    ↓
Move(goblin_42, destination)
```

Authority checks:

```text
Does GMController have possess/control permission?
YES
```

Same `MoveAction`. Same actor. Same movement system.

**No special GM movement code required.**

That is exactly the sort of reuse you want.

### Possession becomes surprisingly simple

Remember your idea of the GM being able to "play as the monster"?

That should not require turning a goblin into a special GM goblin.

You effectively change who controls it:

```text
Before:

Goblin
   │
   └── AIController


GM clicks "Possess"


After:

Goblin
   │
   └── GMController
```

Potentially preserving the old controller:

```gdscript
var original_controller = actor.controller
actor.controller = gm_controller
```

Then when the GM releases it:

```gdscript
actor.controller = original_controller
```

The goblin itself knows nothing happened.

That's a **very powerful consequence of your controller abstraction.**

### GM commands are slightly different

There is another category, though:

```text
"Control this goblin"
```

is different from:

```text
"Spawn 10 goblins."
"Change the weather."
"Teleport everybody."
"Give Mike 10,000 gold."
"Pause the world."
```

Those aren't really actor controls.

So I wouldn't force everything through `GMController`.

Instead Bones could define a general command/action mechanism, while the GM addon provides privileged commands:

```text
GM Addon

GMController
   └── controls actors

GMCommands
   ├── Spawn
   ├── Despawn
   ├── Teleport
   ├── GiveItem
   ├── ChangeTime
   └── SetProperty
```

Both still flow through authority:

```text
GM UI
   │
   ├──── possess goblin ──→ GMController
   │
   └──── spawn dragon ────→ GMCommand
                               │
                               ▼
                           Authority
                               │
                               ▼
                           WorldManager
```

That means Bones does **not** need to know what a GM is.

That's the architectural result I'd aim for.

Bones knows:

```text
Actor
Controller
Action
Command
Permission
Authority
World
```

The GM addon says:

```text
"I can combine those primitives into a Dungeon Master."
```

And that is exactly what a reusable framework should allow.

### It also makes GM optional

A developer downloading Bones from the Asset Store could build:

```text
Single-player RPG
Bones + AI
```

or:

```text
Co-op action RPG
Bones + Multiplayer
```

or:

```text
NWN-like campaign platform
Bones + Multiplayer + GM
```

or:

```text
Turn-based tactical RPG
Bones + Grid Combat
```

They don't inherit a giant pile of GM-specific UI and behavior just because they're using your actor system.

This is starting to suggest a very nice package hierarchy:

```text
                   Godot
                     │
                     ▼
             ┌──────────────┐
             │    BONES     │
             │              │
             │ Actors       │
             │ Actions      │
             │ Controllers  │
             │ Authority    │
             │ Rules        │
             │ World        │
             └──────┬───────┘
                    │
        ┌───────────┼─────────────┐
        ▼           ▼             ▼
   Multiplayer     GM          Inventory
      Addon       Addon          Addon
        │
        ▼
 ENet / Steam /
 Nakama / etc.

                    │
                    ▼
             ┌──────────────┐
             │Misadventures │
             │              │
             │ actual game  │
             └──────────────┘
```

And there's an especially interesting design principle buried in there:

> **A GM isn't a special kind of Actor. A GM is a privileged source of intent.**

That matches the architecture you've been converging on extremely well. Player, AI, GM, scripts, and potentially even remote administration can all become different **sources of intent acting through the same action/authority system**.

That makes the controller abstraction one of the most important things in Bones—not merely an AI/player implementation detail.
