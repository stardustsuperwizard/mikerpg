# Runtime

## Prompt 1
Okay, networking. How tightly coupled is that? If someone wrote a better networking framework could that be subbed in?

## Response 1
Right now, **your networking is more tightly coupled than I would want for something called “Bones.”** The good news is that it is tiny enough that this is easy to fix now.

Your current `network_bootstrap.gd` directly creates `ENetMultiplayerPeer`, hardcodes the port and peer count, writes directly to `multiplayer.multiplayer_peer`, parses command-line arguments, finds `WorldManager`, loads a specific player scene and a specific character sheet, and spawns/despawns players itself. ([GitHub][1]) That means it currently mixes at least three responsibilities: transport, application startup, and game/world behavior.

That coupling also cuts against one of your own stated project principles: MikeRPG should prefer Godot's networking primitives and existing addons rather than hide or replace engine concerns unnecessarily. ([GitHub][2])

What I would want instead is a very small boundary between Bones and whatever networking implementation happens to be installed.

Conceptually:

```text
Bones
   |
   |  "host a game"
   |  "connect to a game"
   |  "peer connected"
   |  "peer disconnected"
   v
Networking Adapter
   |
   +-- Godot ENet
   +-- Steam networking
   +-- WebSocket
   +-- Nakama
   +-- Somebody's BetterNetworkingAddon
```

Bones should care about **multiplayer concepts**, not about `ENetMultiplayerPeer`.

For example, Bones might define a networking contract along these lines:

```gdscript
class_name NetworkProvider
extends Node

signal peer_connected(peer_id: int)
signal peer_disconnected(peer_id: int)
signal connected_to_server
signal connection_failed

func host(config: NetworkConfig) -> Error:
    return ERR_UNAVAILABLE

func connect_to_host(address: String, config: NetworkConfig) -> Error:
    return ERR_UNAVAILABLE

func disconnect() -> void:
    pass

func is_server() -> bool:
    return false
```

Then the default implementation could be:

```text
bones/
└── networking/
    ├── network_provider.gd
    └── providers/
        └── enet_provider.gd
```

`ENetProvider` would contain the stuff you have now:

```gdscript
var peer := ENetMultiplayerPeer.new()
peer.create_server(...)
multiplayer.multiplayer_peer = peer
```

But **Bones itself would not require ENet**.

Then somebody comes along with:

```text
addons/
└── fantastic_multiplayer/
```

and writes:

```gdscript
class_name FantasticNetworkProvider
extends NetworkProvider
```

Your application can choose that instead.

The even more important change is that this part of your current networking code does **not belong in a networking provider at all**:

```gdscript
var world_manager := get_tree().get_first_node_in_group("world_manager")

var spawn_point := SpawnPoint.new()
spawn_point.actor_scene = load("res://scenes/actors/player.tscn")
spawn_point.character_sheet = load("res://data/players/mike.tres")

var actor := world_manager.spawn(spawn_point, id)
```

([GitHub][1])

That's game/application behavior.

Networking should merely announce:

```text
peer 37 connected
```

Then something else says:

```text
peer 37 connected
        ↓
SessionManager
        ↓
Who is this?
        ↓
WorldManager
        ↓
Spawn appropriate Actor
```

That distinction becomes incredibly important later.

Imagine you eventually use Nakama. Nakama might tell you:

```text
User 82 authenticated
Session ABC connected
```

Or Steam might give you:

```text
Steam user 76561198... joined
```

Or a LAN ENet connection might simply give you:

```text
Peer 4 connected
```

Your RPG should not care which one happened.

It should receive something closer to:

```text
PlayerSession joined
```

and act accordingly.

So I'd actually split the architecture into **three layers**:

```text
┌──────────────────────────────────┐
│             MikeRPG              │
│                                  │
│ Player joins → spawn Actor       │
│ disconnect → remove Actor        │
│ permissions / ownership          │
└────────────────▲─────────────────┘
                 │
          session events
                 │
┌────────────────┴─────────────────┐
│       Bones Multiplayer API      │
│                                  │
│ host()                           │
│ connect()                        │
│ peer_connected                   │
│ peer_disconnected                │
│ send / RPC concepts              │
└────────────────▲─────────────────┘
                 │
          provider contract
                 │
┌────────────────┴─────────────────┐
│       Networking Provider        │
│                                  │
│ ENet / Steam / WebSocket /       │
│ Nakama / third-party addon       │
└──────────────────────────────────┘
```

And that answers your question very directly:

**Yes, someone should absolutely be able to write a better networking framework and substitute it.**

In fact, I think that should become a deliberate Bones design principle:

> **MikeRPG Bones defines the multiplayer capabilities it requires, but does not mandate the networking implementation that provides them.**

The built-in ENet implementation then becomes **the reference/default adapter**, not "MikeRPG networking."

That also fits your broader buy-before-build philosophy extremely well. You aren't trying to produce the world's greatest Godot networking library. You're building the RPG framework. If someone else makes a better transport, lobby system, replication library, Steam adapter, or backend integration, **Bones should let you use it.**

And looking at the current file, now is probably the best time to refactor it. It's only 68 lines today. ([GitHub][1]) Six months from now, if spawning, authentication, replication, GM connections, reconnect logic, and persistence have all accumulated there, pulling those responsibilities apart will be considerably harder.

So I would revise our tentative `bones/` structure to something like:

```text
bones/
├── core/
│
├── multiplayer/
│   ├── network_provider.gd
│   ├── network_config.gd
│   └── session.gd
│
└── integrations/
    └── enet/
        └── enet_network_provider.gd
```

And outside Bones:

```text
runtime/
    boot.gd

misadventures/
    player spawning
    player selection
    world joining
```

I actually like **`multiplayer/` more than `networking/`** for the Bones-facing layer. Networking is an engine/infrastructure concern. Multiplayer is an RPG/game capability. That naming reinforces exactly the boundary we're trying to preserve.
