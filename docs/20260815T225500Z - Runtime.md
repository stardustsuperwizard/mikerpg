# Runtime

## Prompt 1
Hm, runtime is going to a problem isn’t it? What happens when runtime is in the addons folder of someone else’s project?

## Response 1
Yes — **runtime is the awkward one**.

`core/` and most of `networking/` can live comfortably inside `addons/mikerpg_bones/`, because they are libraries/framework code. But `runtime/boot.gd` is different: it is effectively part of the **host application's startup policy**. An addon should generally not assume it owns somebody else's `project.godot`, main scene, autoload order, server startup mode, or command-line behavior.

So I would change the boundary slightly:

```text
addons/
└── mikerpg_bones/
    ├── core/
    ├── networking/
    └── runtime/
        ├── runtime.gd
        ├── runtime_context.gd
        └── runtime_interfaces.gd

runtime/
└── boot.gd
```

The important distinction is that **reusable runtime machinery** can belong to Bones, but **the executable bootstrap does not**.

Think of it this way:

```text
Bones runtime:
"Here is how an RPG runtime behaves."

Application boot:
"Start THIS game using THESE options."
```

For example, Bones could provide something like:

```gdscript
# addons/mikerpg_bones/runtime/game_runtime.gd

class_name GameRuntime

func start(config: RuntimeConfig) -> void:
    # initialize framework systems
    # initialize authority
    # initialize networking abstractions
    # initialize world
    pass
```

But the consuming game owns:

```gdscript
# runtime/boot.gd

extends Node

func _ready():
    var runtime = GameRuntime.new()

    runtime.start(
        RuntimeConfig.new()
    )
```

That consumer might decide:

```text
Am I:
- a desktop player client?
- a GM client?
- a listen server?
- a dedicated server?
- a single-player game?
- running editor/debug mode?
```

**Bones shouldn't decide that.**

And this gets especially important for dedicated servers. Your current `boot.gd` may eventually inspect command-line arguments, decide whether to launch server mode, instantiate networking, select a map, etc. That's absolutely application/distribution behavior.

So I'd probably evolve the terminology into:

```text
MikeRPG project
│
├── addons/
│   └── mikerpg_bones/
│       ├── core/          # actors, actions, authority, rules
│       ├── networking/    # transport/network abstractions
│       └── runtime/       # reusable runtime services
│
├── runtime/
│   └── boot.gd            # THIS application's bootstrap
│
├── misadventures/
│   └── ...
│
└── project.godot
```

That gives you a really useful architectural rule:

> **Bones may provide capabilities, but it does not own the host project's lifecycle.**

That rule will prevent a lot of pain later.

It also means the Asset Store package becomes much friendlier. Someone installs MikeRPG Bones and doesn't suddenly discover that it expects to become their main scene or overwrite an autoload. They can instantiate it themselves, or you can provide an optional setup helper/plugin that adds the recommended autoloads.

I would apply essentially the same scrutiny to `networking/`, too. `network_bootstrap.gd` sounds suspiciously application-specific by its name. The actual ENet/server/client abstractions probably belong in Bones; **"start this project's network configuration"** may belong beside `runtime/boot.gd`.

So the separation may ultimately be:

```text
BONES
core/
networking/
runtime/

HOST APPLICATION
boot/
configuration/
main scene
autoload registration
server/client mode selection
```

That is a stronger boundary than just putting all three current directories under `bones/`.

And interestingly, it reinforces your Linux analogy: **Bones can provide the mechanisms; the MikeRPG distribution chooses the policy.** Your actual `boot.gd` is much closer to the distribution's init system than to the kernel/library itself.
